Hello App Review Team,

MenuSearch 0.3.0 (1) is the rejected Store build; the source candidate is 0.3.2 and has not yet been built or submitted. I maintain this independent product and submit under my own developer account. My answers to all nine questions:

1. Function and problem
MenuSearch reads the active app's available menu commands when invoked, shows full command paths, filters them while the user types and executes the selected item. Execution rechecks the target and menu item so a stale result is not silently applied to a different application. Grant Accessibility access in System Settings. With the desired app active, invoke MenuSearch, type part of a command name and choose its full menu path. It uses the current app menus rather than a remotely supplied command catalog.

2. Intended users
Users of applications with deep or unfamiliar menus who want to find commands by name without remembering every location or shortcut.

3. Product contribution
The 0.3.2 source candidate also stops shortcut recording when its settings window closes or loses focus, limits recording to the active settings window, and validates imported shortcut key codes and modifiers more strictly. These changes have not yet been verified in a frozen Store binary.

It is a focused native live-menu workflow with full paths, keyboard filtering and guarded execution. Users need not install a larger launcher or plugin platform to use this one function. A full path disambiguates commands with similar names, while checking the target before execution handles changes in the active app. The need is a small keyboard workflow for deep application menus, without adding file search, plugin management or other launcher functions.

4. Testing and beta feedback
Pre-submission records include internal pure-logic tests, Store/direct-download compilation, package checks and sandboxed offscreen settings/UI checks. These are internal validation, not external beta feedback. I do not invent user-feedback examples.

5. Related apps
It is standalone. Initials switches apps; MenuSearch executes commands inside the current app; KeyScope diagnoses shortcuts. Sift, Clip and Tempo operate on different data and user tasks.

6. Why standalone
It could be added to a larger launcher, but menu traversal/execution and its permission flow differ from letter-based app navigation. Independent installation serves people who already have an app switcher and only want menu search.

7. Shared developer code
AppConfiguration.swift provides shared author-maintained settings import/export and optional sync. LaneSignal.swift is common launch/diagnostic infrastructure. The Store design excludes the updater UI and user-facing CLI. The candidate source set now also includes AppLifecycleCLI.swift and calls follow(configuration); its compatibility with the excluded updater types must be checked before this candidate can be described as buildable. Menu traversal, filtering, hotkey registration, the panel and guarded execution are MenuSearch-specific. AppConfiguration is also used by Sift and Clip; LaneSignal is also used by Initials, Sift and KeyScope.

8. Third-party code
This code evolved from my own MacKit menu-search prototype, as disclosed in the README. Raycast's public behavior was a functional reference, not source code incorporated into this app. The declared target uses Apple frameworks and no third-party menu-search implementation.

9. Product ownership
I own the product, concept and branding and submit under my own account. It was not commissioned by a client or submitted for an external content provider.

Please continue evaluating this submission. If a concern remains, please identify any specific existing app, duplicated functionality or source component that remains a concern so I can address it directly. Thank you.
